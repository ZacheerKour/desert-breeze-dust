## P1 items
---------------------------------------------------------------------------

### 1. RECOMP_GUEST_LOCK never covers the main game thread (ours bug; upstream fixed it)
- Ours: guest lock = ours:9786-9864 (guest_cpu_join/part, kernel_thunk_dispatch). The main thread joins in xbox_kernel_bridge_init (10117) and holds the lock. At its first kernel call (PsCreateSystemThreadEx) kernel_thunk_dispatch releases it (9849-9850), then the bridge calls fn() inline (686-693). Inside that, every nested kernel call sees t_guest_held == 0 and does nothing, and the re-acquire test is `t_dispatch_depth == 0` (9858) but depth is stuck >= 1 for the thread's life (the outer call never returns). Result: with RECOMP_GUEST_LOCK=1 the main thread runs unserialised against every worker; only workers take turns among themselves.
- Upstream: up kernel_bridge.c:887-901 and 9220-9227 wrap the inline main-thread call in xbox_GuestCpuEnterCallback()/LeaveCallback(): "take it back for the thread's whole life ... or the main thread runs unlocked against every worker, the race the lock is for". Same wrapper at :699-707 (bridge_run_thread_inline), :2314 and :4461 (APC), :2616 (KeSynchronizeExecution), :4641 (unwind handler). Their lock state is a held flag (kernel_guest_cpu.c t_held), not a depth, so nested callbacks restore what they found (up 10788-10803).
- Why it matters: every earlier GUEST_LOCK A/B in docs/RECOMP_ANALYSIS.md (450-485 "no evidence the lock is needed", 467, 712 "did not help, 3 of 6 bad") tested a lock that excluded the main thread. Those negative results are not valid evidence.
- Port: minimal fix = in the is_first_call branch (ours:686 and 8250) take the lock before fn(), and use a held flag instead of depth in kernel_thunk_dispatch. Effort 2-4 h plus redoing the lock A/B. Credit apexJCL/BearddOddity. Priority P1.

### 2. KeSynchronizeExecution gives no exclusion (ours bug; PD's only call site is DSOUND)
- Ours: bridge_KeSynchronizeExecution ours:2352-2378, comment "ponytail: no lock is taken": it just calls the routine. PD calls it once (0x1C3008, DSOUND range 0x1BA180-0x1C41E0) to touch APU state against the APU ISR (apu_core.c:159-190 delivers vector 5 from its own thread). Our pd-ojl CPU lock (kernel_hal.c:196 cpu_lock_enter) is taken only on an IRQL crossing to >= DISPATCH, so it does not cover this routine, which can run beside the ISR it exists to exclude.
- mc kernel_bridge.c:2824-2832: KfRaiseIrql(31) around the routine (takes the dispatch lock), KfLowerIrql after. up 2583-2615: DispatchGate around it, plus callback_regs_save/restore with the routine's result kept in g_eax.
- Port: wrap fn() with xbox_KfRaiseIrql(26..31) / xbox_KfLowerIrql(old) (irql_track takes g_cpu_cs for any level >= 2); keep g_eax across the lower. Effort ~1 h. Credit mcdub / apexJCL. Priority P1 (same family as the pd-ojl USB TD-allocator corruption, on the DSOUND/APU side).

### 3. File-I/O APC delivery leaves the guest stack 12 bytes high (ours bug; upstream fixed it)
- Ours: deliver_one_apc ours:3533-3559 pushes 4 dwords (0, iostatus, ctx, dummy return = 16 bytes), calls fn(), then `g_esp += 12`. The callee (NtUserIoApcDispatcher thunk: dispatch pops 4 + 12 arg bytes, case 232 at 8918; or a lifted stdcall `ret 12`) already consumes all 16, so each delivery leaves esp 12 above where it started. The calling bridge (NtReadFile, 3850) then reads STACK_ARG(0) for bridge_handle_is_async (3865) from the skewed esp, and the dispatch epilogue adds its arg bytes from there. Callers that exit with `leave` hide it. PD uses this path: RECOMP_ANALYSIS.md:467 "kernel completes NtReadFile APCs (apc=0xFE000044 = NtUserIoApcDispatcher) inline", and the loader behind the unsolved chain crash (line 630) goes through it.
- up kernel_bridge.c:4434-4470: "Restore esp from before the frame rather than adding a fixed amount back ... FBoS's wait wrapper sub_000907CB does `pop esi` first and came back with a stack address in its caller's esi", plus callback_regs_save/restore. Our text equals the pre-fix text (td and dj identical to ours).
- Port: save g_esp before the push, restore after fn() (two lines); optionally copy the CallbackRegs helpers. Effort 0.5 h. Priority P1: trivially cheap, and a plausible contributor to the stack-sensitive crashes. The link to the chain crash is a hypothesis, not proven.

### 4. Pin guest threads to one host core (cheap mitigation; three forks do it)
- Ours: no SetThreadAffinityMask in src (grep). Guest threads run on any core.
- up kernel_thread.c:449-530 (xbox_GuestCpuMask, xbox_GuestThreadPin; opt-in RECOMP_GUEST_CPUS=one|<n>), called at up kernel_bridge.c:752 (worker), 887 and 9220 (main). td kernel_thread.c:526-790 does it by DEFAULT (RECOMP_GUEST_CPUS=all opts out): on Windows it avoids core 0 and its SMT sibling ("title thread pinned there stalled 20-90 ms", td 560-590) and raises the process priority class to ABOVE_NORMAL while pinned (host_priority_apply td 704-740, with a measured table: a pinned thread starves behind normal-priority work when the process runs below normal, e.g. started from Task Scheduler). dj kernel_bridge.c:481-520 pins every guest thread AND the timer thread to logical CPU 2 and sets the timer thread TIME_CRITICAL (dj 3153-3165) so a title spinning at raised priority cannot starve the DPC that acknowledges the GPU.
- Problem solved: "slot = count; fill; count = slot+1" shared pools (BLiNX 2 black terrain, up/td comment); Def Jam movie ring count-then-pointer publication race. Same class as our unverified pd-ciz/pd-dz0 hypothesis (RECOMP_ANALYSIS.md:450). Does ours have the bug: the class, yes (parallel guest threads, no ordering); whether PD hits it is unproven.
- up and td keep the timer/DPC and device-model threads OFF the pin; only dj pins the timer thread. td warns pinning cost frames on one Ryzen (thread waited for its idle core to wake after sleeps), so A/B it. PD guest uses about 0.9 core total (RECOMP_ANALYSIS.md:617), so one core should hold.
- Port: copy xbox_GuestCpuMask/xbox_GuestThreadPin (about 80 lines, Windows part only) into kernel_thread.c, call from bridge_thread_main (ours:544) and the is_first_call branch; add the priority-class raise only if pinning is adopted. Effort 2-3 h plus A/B. Credit apexJCL (up), td authors, Vlad Yanhursky (dj). Priority P1 as an experiment: cheapest approximation of "one CPU", no relift.

## P2 items
---------------------------------------------------------------------------

### 5. Replace the plain critical-section guest lock with upstream's quantum / hand-off scheduler (+ lifter back-edge yield)
- Ours: the guest lock is a bare CRITICAL_SECTION released and re-taken around EVERY kernel call, KfRaiseIrql/KfLowerIrql included (ours:9843-9864). No fairness (barging), no quantum, no loop preemption. Our own ponytail note (9786-9803) admits a kernel-call-free guest spin deadlocks it.
- up src/kernel/kernel_guest_cpu.c (487 lines, new file; hooks up kernel_bridge.c 10758-10805, rtl 513). Its header gives measurements: attract mode 32 flips/s lock off, 28.5 with a plain critical section, 12.7 with a fair ticket lock that switched at every call. Design: a kernel call is a "soft release" and the caller barges back if nobody took the CPU; calls that may block wake waiters (ordinal_may_block: 99,158,159,190,196-202,207,219-237...); a thread past RECOMP_GUEST_QUANTUM (4 ms) with a waiter hands over at the next kernel call or loop back edge; oldest waiter is granted (ticket) and barging is refused until it has run; waiters re-poll every 2 ms so a bridge missing from the list costs latency, not a hang; NtYield and thread end hand over at once; no hand-off while IRQL >= DISPATCH. Stats line `[GUEST] cpu: turns/switches/waits/longest wait`. Tests: up tests/guest_cpu, tests/kernel_guest_cpu.
- Back-edge preempt needs a relift: up tools/recomp/translator.py 441-466 (_mark_back_edges), 528-530, 3083-3084; __main__.py 280 (--back-edge-yield); templates/runtime/recomp_types.h 1181-1200 (RECOMP_BACK_EDGE: one relaxed load per loop back edge). Ours translator.py has none. Without it the scheduler works at kernel calls only; a pure guest spin is not preempted.
- mc alternative (mc kernel_bridge.c 570-880, default ON): FIFO ticket GIL; g_gil_contended polled at every function entry (RECOMP_PREEMPT) after 1 ms of waiting; optional priority-eager hand-over (RECOMP_GIL_EAGER); clock-read ordinals keep the lock (kernel_call_keeps_gil 10301); wait/CS ordinals try first and release only to block (kernel_call_tries_first 10329, bridge_block_begin/end 10347); gil_yield_wait (830) so Sleep(0)/NtYield polls wait up to a 10 ms quantum instead of re-taking the lock at once (called from KeDelayExecutionThread with a zero interval, mc 2560). Rationale (NFSU2 worker read allocator 0xAA fill as a pointer; MC3 on Switch lost 66-75% of main-thread time to hand-overs) is Switch-flavoured; upstream's design is the cleaner base.
- Ours has the Sleep(0) starvation: xbox_KeDelayExecutionThread with a zero interval is SwitchToThread (kernel_thread.c:170) while the lock is released and the waiter not yet awake. PD has 3 KeDelayExecutionThread sites.
- Also take with it: xbox_GuestCpuBlocked() in kernel_rtl.c:513 (wake waiters before a contended CS blocks), and EnterCallback wrapping at every bridge-run guest call (APC, unwind handler); ours runs those unserialised.
- Effort: file + hooks 1 day; relift with --back-edge-yield and regression 0.5-1 day (needs host_time.h xbox_HostNowNs and xbox_IrqlThisThreadBlocksDpcs, which ours can answer from t_cpu_held in kernel_hal.c). Credit apexJCL. Priority P2 (P1 if item 1's re-test shows the lock helps and it is to become default).

### 6. Real thread identity and priorities (KeSetBasePriorityThread is a silent no-op in ours)
- Ours: bridge_KeSetBasePriorityThread ours:4585 passes XBOX_TO_NATIVE(guest arg) to xbox_KeSetBasePriorityThread(PVOID), which uses it as a Win32 HANDLE (kernel_thread.c:241-256). The guest arg is the fake ETHREAD VA returned by our ObReferenceObjectByHandle (4359-4375), not a HANDLE, so Get/SetThreadPriority fail and nothing happens. KeSetPriorityThread (7754) and KeGetCurrentThread (7790) are stubs returning 0. ObReferenceObjectByHandle(NtCurrentThread = -2) finds no entry in s_thread_objs and returns object 0. PD uses these (XAPI SetThreadPriority 0x1457DD..0x1457FF; ObReference at 11 sites).
- up kernel_bridge.c:513-700 (thobj_*): refcounted guest thread objects from contiguous pages, token-to-object map, NtCurrentThread object (thobj_current), KTHREAD.TlsData at +0x28 with fs:[0x28] = the object (bridge_layout_tls 480-510), ExitStatus then SignalState published on exit, a shadow host-thread handle so KeWaitForSingleObject on the object waits on the thread; new ObReferenceObjectByHandle at up 5310-5330. td identical.
- mc kernel_bridge.c:455-545 and 5155: KTHREAD = TIB address with a table to host HANDLE; KeSetBasePriorityThread/KeSetPriorityThread/KeGetCurrentThread really work; xbox_abs_priority_to_win32 (8286). Its stated rationale: all guest threads ran at one priority and titles depend on console ordering.
- Ours also leaks the 0x200-byte ETHREAD per thread (comment near ours:480) and every guest thread shares one fs:[0x28] object, because xbox_AllocThreadTib (xbox_memory_layout.c:3074-3103) memcpy's the main TIB.
- Value for PD: today "raised-priority worker runs first" is faked only by spawn_gate (item 7). Recording the guest priority per thread is the prerequisite for any priority-aware hand-off; applying it to the host thread is optional and carries starvation risk. Effort 0.5-1 day (take up's thobj block or mc's smaller table). Priority P2.

### 7. Priority-aware hand-off instead of the time-bounded spawn gate
- Ours: spawn_gate (ours:468-478, 585-620, 9847): the creator waits (<= 50 ms) until the new thread's first kernel call. Fixed the _ERROR_ profile race (12/12 launches) but it is an approximation. On the console the sequence is: CreateThread returns, the creator's SetThreadPriority (KeSetBasePriorityThread, 0x1457FF) raises the child above itself, and the child runs until it blocks or ends. The gate releases the creator at the child's first kernel call, before the child necessarily read its shared parameter block (ctx 0xB65B0 / block 0x39AAA0, RECOMP_ANALYSIS.md:714). A child that makes several kernel calls first can still lose the race.
- td src/kernel/kernel_wake.c/.h (284 lines), "a woken thread of higher priority runs first (BO-221)": per-thread guest priority (xbox_WakeSetPriority from KeSetBasePriorityThread), a list of ordinals that can block (xbox_WakeOrdinalBlocks: 99,158,159,190,202,219,233-236,238,277), the signaller waits until the woken higher-priority thread makes its next blocking call, bounded 3 ms; RECOMP_WAKE_HANDOFF=0 disables. BUT the signal path is compiled out on Windows (xbox_WakeSignalled: `#if defined(_WIN32) (void)object`, because a Win32 event does not say which wait took it), so td itself does not use it there.
- mc kernel_bridge.c:970-1060 takes the other approach: threads are created suspended and started at the creator's next kernel call (or by the timer thread after 5 ms), and CreateSuspended is honoured. Ours ignores CreateSuspended (ours:650-745; bridge_spawn_thread has no such argument). PD's XAPI passes the title's CREATE_SUSPENDED bit straight through (sub_00145A02: arg7 = (flags>>2)&1), so a title that creates suspended and resumes later is started early by ours. No PD call site is known to do this.
- Hardening for PD: release spawn_gate at the child's first BLOCKING call (td's ordinal list) or exit rather than its first kernel call, ideally inside KeSetBasePriorityThread when increment > creator's (needs item 6). Effort 1-2 days. Credit td/mc authors. Priority P2.

### 8. Timer/DPC thread must not block on the DISPATCH gate; DPC and ISR delivery order
- Ours: kernel_timer_thread (ours:2889) runs vblank tick, DPC drain and timers on ONE thread. kernel_run_dpc (2280-2335) and the vblank ISR (kernel_raise_interrupt 2500, 2614) enter through xbox_IrqlEnterInterrupt, whose cpu_lock_enter spins in SwitchToThread for up to 200 ms (kernel_hal.c:196-240). A guest thread parked at DISPATCH (our own docs: D3D vblank DPC holds of 50-1400 ms, pad dead for seconds, RECOMP_ANALYSIS.md:646) therefore stalls vblank delivery and all timers for that long. The hold-off in apu_core.c:162 (`xbox_IrqlBlocksInterrupts() && ++held_off <= 50`) is the old check-then-act that pd-ojl removed from OHCI; it is harmless only because EnterInterrupt then takes the gate.
- up kernel_hal.c:200-340 and 540-770: the drain uses gate TryEnter ("never waits for it: this thread is also the vblank and timer source, which a guest parked at DISPATCH must not stop; what is queued stays queued for the next tick"); interrupts are POSTED to the gate holder and run at its next safe point (xbox_IrqPost/xbox_IrqSafePoint; every kernel call is a safe point, up 10815); DPCs optionally run on the guest thread that lowers IRQL (xbox_DpcOnRaise). All behind RECOMP_DISPATCH_GATE=1, off by default upstream because "#192 ... has an untraced Burnout 3 boot hang" (up README 1026) and one B3 run in a few stalled at its first movie. dj kernel_hal.c:269 xbox_DispatchLockEnter is the bounded ~200 ms version (equal to ours).
- Smallest port: in kernel_drain_dpcs use TryEnterCriticalSection(g_cpu_cs); if busy leave DPCs queued and skip the vblank ISR this tick. Effort 0.5 day (try-enter) to 1-2 days (full post-to-holder design, with upstream's own hang risk). Priority P2.

### 9. Guest-built dispatcher objects (KEVENT written inline by the title) are opt-in per VA in ours
- Ours: ke_guest_event (ours:6612-6665) is active only with RECOMP_TITLE_KEVENTS=1 or for VAs registered via xbox_EnableGuestEvent (one slot in use for pd-vnc). Any other inline KEVENT has no shadow: KeWaitForSingleObject falls to `h = XBOX_TO_NATIVE(object)` (ours:1830-1836), an invalid HANDLE, so the wait fails at once and returns STATUS_UNSUCCESSFUL (kernel_sync.c WAIT_FAILED mapping); KeSetEvent does SetEvent on a bogus handle. Callers that loop on the status spin (dj comment: "36M calls in 8 s"). Our DSOUND GetStatus spin (RECOMP_ANALYSIS.md:467-469) looks similar but was traced to a stream state word, not shown related.
- td kernel_bridge.c:7669-7710 ke_event_shadow: always on, builds the shadow from the header (Type 0/1, SignalState at +4) under the table lock; used by KeSetEvent/Wait/WaitMultiple (td 1925, 5909). up ke_guest_event_prepare (1990) and auto-reset consumption after a successful WaitMultiple (up 5844-5890; dj 5321 same). mc kdisp_* (2062-2215) keeps the guest header as the truth with a condition variable and also handles KSEMAPHORE.
- PD relevance: KeWaitForMultipleObjects (1 site 0x1C58AD; ours:4887 has no guest-event path at all), KeSetEvent, KeWaitForSingleObject. Measure first: count waits/sets whose object is in neither the shadow table nor the handle table. Effort 2-4 h with td's ke_event_shadow. Priority P2.

### 10. Timer re-arm leaves guest SignalState stale
Ours kernel_set_timer (ours:2984) resets the shadow event before publishing (better ordering than up/mc) but never clears the guest header; the timer thread sets it to 1 on fire. dj (dj 3276-3310) clears BRIDGE_MEM32(timer_va+4) under the lock. Only matters if guest code reads the header directly; PD imports no KeReadStateTimer-like call. 5 min.

### 11. Guest-relative millisecond clocks (KeTickCount, KeQueryInterruptTime)
Ours: KeTickCount is written by the NV2A ack thread loop as GetTickCount() (xbox_memory_layout.c:1105-1112); KeQueryInterruptTime = GetTickCount64()*10000 (kernel_hal.c:1213). Host uptime, coarse unless the timer period is raised (not checked). dj kernel_hal.c (xbox_GuestUptimeMs, "patch 0067") makes both QPC-based and starts the guest 10 s after process start: days of host uptime made a title's float/32-bit clock math lose bits (Def Jam intro movie stalling), and 15-16 ms jumps rounded elapsed time up to whole game steps. up kernel_clock_ms (up 2817) is QPC-based for Wine. PD has a long game-speed/subtitle-clock saga; test before adopting. 1-2 h. P3 (maybe P2 for PD timing).

### 12. Critical-section shadow table (shared by every fork; none fixes it)
kernel_rtl.c:190-250: slots keyed by guest address are never freed; there is no delete path (PD imports no RtlDeleteCriticalSection); RtlInitializeCriticalSection (528) does not reset an existing shadow, so a CS re-initialised at an address whose old shadow is still locked stays locked; at 4096 distinct addresses further locks are silently UNPROTECTED (xbox_cs_shadow returns NULL, enter/leave become no-ops). At least add a counter/log. 1 h.

### 13. Smaller items
- Ke shadow table: ke_shadow_insert (ours:6505) closes the previous host handle when the same VA is re-initialised while a waiter may be inside WaitForSingleObject on it, and lookups hand out a handle after dropping the table lock (use-after-close window). No fork fixes it. P3.
- mc kernel_rtl.c:471 xbox_RtlEnterCriticalSectionIfFree + kernel_call_tries_first: a speedup only when the guest lock is on. Part of item 5.
- td xbox_log_thread_role / thread_set_os_name (td kernel_bridge.c:533-600): names host threads (SetThreadDescription) and registers them with a hang reporter; cheap aid for race hunts. 1 h.
- up kernel_thread.c:435-438 guards worker-stack slices against a runtime stack region; ours XBOX_STACK_SIZE is a compile-time 8 MB, so not needed.
