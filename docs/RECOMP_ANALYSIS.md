# xboxrecomp analysis of Phantom Dust `default.xbe`

Run 2026-10-14 with xboxrecomp v0.13.1 (commit `193e299`, cloned to `xboxrecomp/`), capstone 5.0.7 in `.venv-recomp/`. Only the four analysis stages were run (`xbe_parser`, `disasm --text-only`, `func_id`, `abi_analysis`); the lifter (`recomp`) and runtime were NOT run. Outputs are in `recomp-analysis/` (JSON databases, `asm/text.asm`, logs, `stats.py`/`stats2.py`). Counts are static-analysis results, not a statement that the game works.

- Total `call` instructions 23,162; **indirect calls 1,199 (5.2%)**: 655 through `[reg+off]` (virtual calls), 155 through a register, 389 through an absolute memory slot (383 of the xrefs are kernel-import calls; the rest are global function pointers).

- MMX ~650.

## What this says about viability
- **Size**: about half of Burnout 3's 22,097 lifted functions, 1.7 MB `.text`: favourable.
- **Not a typical RenderWare game**: weak automatic identification, heavy C++ virtual dispatch: the main unknown.
- **ABI confidence is low for most functions**: needs the toolkit's conformance/ABI-check workflow and probably manual overrides.
- **Instruction risks are concrete and small in number** (a few dozen `lahf/sahf/fldcw`-class sites), which is manageable if the lifter's recent fixes cover them (unverified here).
- The decisive unknowns are still dynamic: threading (the game imports `PsCreateSystemThreadEx`), the statically linked D3D8LTCG device context, and audio.

## Crash root cause found and fixed (2026-10-14, overnight session)
Corrections to the notes above: (a) the "heap allocator `sub_00148375` + `NtAllocateVirtualMemory` out-parameters" theory in Iteration 2 was **wrong**; the shim's commit-on-existing path is harmless here (both commits were page-aligned). (b) The first crash-function attributions were wrong twice: once because I read leftover values off the guest stack as a call chain, once because I assumed the high bits of the image RVA under ASLR. The reliable method: print `module base`/RVA in the crash handler, map it with a linker `/MAP` file, then confirm with a write-watch.
What actually happened (verified by instrumentation in the diagnostic copy `pd-game-trace/`, which is scratch only):
1. The crash is a read through `eax = 0xFFFFFFF7` in `sub_00148BCA` (guest 0x148E01, `mov ecx, [eax+8]`) while walking a heap free list: the free-list head array at `seg+0x180` of the heap segment at guest VA `0x00F81000` was corrupted (103 of 128 heads out of range).
2. A write-protect watch on that page caught the writes: `RVA 0xD37237/0xD37249/0xD3725D`, i.e. the second loop of guest function `sub_001601F0` (`byte [esi]=0; dword [esi-0xC]=-1; byte [esi+1]=0`, stride 0x14), running with `esi` pointing into the heap instead of the table at `0x317944`.
3. In that loop, `esp` after the call to `sub_001689C0` was 16 bytes lower than it should be and `esi`/`edi` were clobbered (values popped from the wrong stack slots).
4. `sub_001689C0` calls `sub_001BC7F8` (lifted correctly, ends `ret 16`), which calls `sub_001BC6B0`. That one was **not a lifted function but one of the 532 "unresolved call target" stubs**: `void sub_001BC6B0(void) { g_esp += 4; /* not detected */ }`. The real code at 0x1BC6B0 is stdcall with 4 arguments (`ret 0x10`), so each call leaked 16 bytes of guest stack, corrupting callee-saved registers and finally the heap.
5. Fix: seed all unresolved direct-call targets as real functions through the toolkit's own gates (`tools.seed_from_log` fed a synthetic log of the 532 addresses: 524 accepted, 8 rejected as outside executable sections), then re-run disasm/func_id/abi/lift (fresh project `pd-game-v2/`). Functions 10,829 -> 11,494 (11,551 lifted, 0 failed, 61 untranslated sites, 644 stubs remain because seeding exposes new unresolved targets). **The heap corruption disappeared and the run got much further** (about 2,000 log lines vs 538).
General lesson: the "not detected" stubs only pop the return address (or a `ret N` they happen to find), so any real stdcall function behind a stub corrupts the stack. They are a placeholder, not a fix.

## Overnight bring-up results (2026-10-14 night to 2026-10-15)
Working project: `pd-game-v2/` (lifted code regenerated each cycle by `pd_iterate.py`; `run_game.bat` launches it). **Current state: the recompiled game boots through CRT/XAPI startup, DirectSound hardware init and D3D hardware init, the GPU command buffer is consumed, the game's vblank handler runs, a screen clear executes and a 640x480 window opens, but the frame stays black (0 draws) and the main thread is stuck in a D3D display-mode setup loop. No audio, video, input or gameplay. It is not playable.**
Chronology of what each fix was and the evidence:
1. **Unresolved-call stubs leaked stack** (root cause of the first crash; see the previous section). Seeding them fixed the heap corruption.
2. **Disassembling only `.text` (`--text-only`) left the library sections (DSOUND, D3D, XNET, XONLINE, XPP, XMV, WMADEC, XGRPH) without function/jump analysis**, so their function boundaries came only from calls out of `.text`. Re-running with all executable sections (default, no `--text-only`) raised functions 11,494 -> 12,578 (D3D 72 -> 307, DSOUND 32 -> 400, XNET 27 -> 432, XONLINE 71 -> 847, XPP 11 -> 271) and cut unresolved stubs from 644 to ~245.
3. **Truncated functions (two-level `switch` with a jump table, e.g. `sub_0014B060`) lost their case blocks and epilogue**, returning with `esi` clobbered and the stack unbalanced; this broke `sub_000B0A20`, which made the game's run loop receive `this = 1` and spin on a null virtual call. Found with `RECOMP_ABI_CHECK` (logs each lifted call that returns with callee-saved registers changed or `esp` too low) plus per-function entry/exit traces. Fix: compare the toolkit's function extents with Ghidra's (`ghidra-scripts/PdExportFuncs.java` -> `ghidra_funcs.json`) and extend each truncated function to the end of Ghidra's contiguous range (`pd_extend_ends.py`, 169 functions, 80,928 bytes), keeping interior entries. After this the build has no crash, no failed indirect calls and no null-call loop. The toolkit's own `--coalesce-functions` could only handle 7 of the 216 truncated candidates because the rest have real call targets inside them.
4. **Runtime switches needed** (from the toolkit docs, verified here): `RECOMP_AC97_READY=1` (without it DirectSound init spins forever on the audio codec), `RECOMP_PB_EXEC=1` (execute the GPU command buffer), `RECOMP_VBLANK=1` (vertical-blank events), `RECOMP_FB_WINDOW=1` (window on the guest framebuffer). `RECOMP_WATCHDOG_SECS=N` prints the main thread's registers/stack when it stops making progress; my scratch `main.c` also has `RECOMP_SAMPLE=1` (samples every thread's native position, mapped with the linker map).
Current GPU report: DMA_PUT/GET advance (0x4000 -> 0x4C08), `[GPU] clear colour 0x00000000`, "268 unhandled methods (152 distinct)", 0 draws, 0 pixels written. Two privileged instructions were reached and treated as no-ops (`wbinvd` at 0x24AA15, `out dx,al` at 0x24C031, D3D hardware init).
Remaining ABI flags with the check on: the SEH prolog/epilog helpers and the stack probe (expected), `sub_001B28F0` (ebx), `sub_00245AB8` (D3D, ebx/esi/edi).
**Diagnostic method that worked** (reusable): (a) map the crash RVA to a function with the linker `/MAP` file after printing `module base` in the crash handler; (b) `RECOMP_ABI_CHECK`; (c) `--trace-functions` JSON lists for a handful of functions plus `RECOMP_TRACE_ARGS`; (d) a write-protect watch on a corrupted page to catch the writer; (e) Ghidra-vs-toolkit extent comparison for truncated functions.
**Mistakes made and corrected along the way:** wrong crash attributions (stale stack values, ASLR RVA), a heap-allocator theory that was wrong, and an "extended ends" test that silently ran the old binary because my build call produced no output. Always confirm a rebuild actually happened (check the exe time or a changed behavior) before reading a test result.

## Breakthrough 2026-10-15 (rendering)
The earlier "display-mode wait loop" diagnosis was wrong. Real stalls, in order:
1. D3D fence: the guest waited for the word at 0x80003000; NV2A semaphore methods 0x1D6C/0x1D70 were unimplemented. Added to the clone's `nv2a_pb_exec.c` (backup `.bak-20261015`). The semaphore DMA base is hacked to physical 0x3000 (`RECOMP_SEM_BASE` overrides).
2. DSOUND: `sub_001BCDCF` spins on a DSP command word at 0x83050810, so `RECOMP_APU_DSP_ACK=0x83050810`.
3. Truncated functions split by seeded `seed_vtable_thunk` fragments (0x77080 was cut at 0x7709D, so a callee left the stack 8 bytes off, `edi` became 0x64, and `sub_000B7C70` walked a list forever). Fix: `pd_extend_ends.py` now also follows jmp/jcc closure (410 functions extended). Unresolved stubs 245 -> 46.
Result: the title logo renders, draws exceed 160, and `bgm/31_Title.stx` loads. About 1 FPS.
Tools: `stackmap.py` (watchdog guest stack to functions), `mapsample.py` (RECOMP_SAMPLE RIPs to /MAP symbols).

## The post-profile black screen: root causes found (2026-10-15, late)
1. **A stale all-zero profile caused the original black screen.** The runtime keeps saves in `extracted/UDATA/4d530046/<profile>`; an early test run wrote `profile.dat` (13,312 bytes, all zero) and every later boot reloaded it. Moving that folder aside (`bak-profile-20261015/`) makes the game show the profile name-entry screen after Start, then Down, then A (on-screen keyboard, default name "Phantom Dust", Start accepts). UI text renders correctly; the background is garbled (see beads `pd-a0t`).
2. **Lifter bug (fixed): one-operand 8-bit `imul`/`mul`/`div`/`idiv`.** `imul cl` (AX = AL*CL) was lowered as a 32-bit multiply that also wrote the high dword to EDX, clobbering DL. ## 2026-10-16: XMV MOVIES FIXED (root cause: untranslated `in al, dx` -> display field never alternated)

## 2026-10-17 - Contiguous arena root cause and state at pause
- The 64 MB contiguous arena is eaten by the game's own pattern: a fixed 44 MB pool (`0x2A80000`, requested from guest 0xB2920) at boot, plus a 0x258000+0x12C000 frame/Z pair re-created on every video-mode change (opening movie, demo movie...). ## 2026-10-17 - Movie flashing and black movies: stale texture alias + arena exhaustion (both fixed)

User video (attract-mode gameplay demo): every other group of frames black with only the "Press START" overlay. Reproduced in attract mode (window brightness alternating ~55-65 vs ~8, flips at ~150/s = the user's 144 Hz monitor vsync).

1. **Flashing = stale render-surface alias.** The movie player double-buffers two 640x480 textures. The second buffer (offset 0x02589000) lay on top of an old 512x512 render target registered at that address during the menus; `hw_texture` resolves a texture to an existing surface at the same offset ("render-to-texture alias") and picked that stale black target instead of reading the decoded frame from guest memory. Every second movie frame therefore drew black. Evidence: `RECOMP_HW_PRESDBG` (backbuffer mean per present) + `RECOMP_HW_TEXDBG` (`[TEX]`, `[TEXH]`, `[CLR]`, `[DRW]`, `[DRW2]`; armed by creating `presdbg.flag`) showed `ALIAS-SURFACE off=82589000 512x512 drawn_frame=30961` for texture 640x480 while the movie ran. Fix (nv2a_hw_d3d11.inc, .bak13): ignore the alias when its width differs from the texture's and it was not drawn in the last 4 frames. `RECOMP_HW_ALIAS_OLD=1` restores the old behaviour.
2. **Black movies after the first demos = the arena leak again.** From the 3rd movie on, draws were 0 per frame: the game's new frame-buffer allocation returned NULL (arena exhausted), so it rendered to surface offset 0, which `hw_surface()` rejects. `RECOMP_CONTIG_RECLAIM` fixes both this and the earlier crash; it is now ON by default (`RECOMP_CONTIG_RECLAIM=0` disables). Only blocks >= 1 MB are reused (`RECOMP_CONTIG_MIN`) and alignment gaps are not offered for reuse.
3. Verified: with reclaim + alias fix, a full 13-minute attract cycle (advdemo, playdemo0, playdemo1, advdemo again) shows pictures throughout (2 of 42 samples dark, fades), no exhaustion, no crash. Default build (no env flags) reaches the Clinic through the `_ERROR_` profile stably.

### USB pad polling dies after minutes (found while doing the above) - the likely root of pd-dz0
- Symptom (runs n5/n6/n7, also earlier "stuck dialogue" episodes): the game keeps rendering at 30 FPS but ignores every button (dialogue at its last page cannot be dismissed, pause menu does not open). In the log the `PAD: live` lines stop: `pad_live_poll` only runs when the guest polls the pad, so the guest stopped polling.
- Evidence from the dead process (n7, `peek`): the pad's interrupt ED (physical 0x1A30, in HCCA slots 0/8/16/24) had **HeadP = 0xFFFFFFF0** (ED = `00201081 00002EA0 FFFFFFF0 00000000`), TailP 0x2EA0, and the live TD at 0x2E80 (`E1140102 ... NextTD=0x2EA0`) was still pending, i.e. the model had written `head = next` where `next = rd32(td+8) & ~0xF` = 0xFFFFFFF0. The XPP driver marks an unchained TD with NextTD = 0xFFFFFFFF (the free pool at 0x2E40.. is full of it). The walk (`ohci_walk_eds`) took the NextTD of a head TD that the driver had not finished building / had already recycled and stored it as the new HeadP; the driver then never gets a completion and stops polling the pad (and, when it follows the pointer itself, it writes to guest VA 0xFFFFFFFF in `sub_0025C825`, which is in the XPP section: this matches the pd-dz0 crash e1 exactly).
- Fix (toolkit `xboxrecomp/src/usb/ohci.c`, backup `.bak-20261018h`): (1) if a queued TD's NextTD is 0xFFFFFFFF leave it for the next pass (logged `[OHCI0] ED ... has NextTD 0xFFFFFFFF; left for the next pass`); (2) write HeadP back only when the pass changed it and only by compare-and-swap against the value that was read (the old code stored the snapshot back unconditionally, clobbering a concurrent driver update; logged `HeadP changed under the walk`). Both are no-ops when the race does not occur. Not yet proven to remove the death (run n8 has them in and has run ~60 min with the pad alive, no guard line printed yet, but the failure took 5-25 min to appear before and is not deterministic); n8 also had `dw 80001A38 F0000000` armed (write watch that reports only HeadP values >= 0xF0000000).
- n8 pad soak after the OHCI change: `padsoak.sh` (random walk/A presses, each command verified by the log line count of `PAD: live`, abort on a dead pad) ran 9 + 9 minutes plus the whole quest002 start from the terminal and a tutorial (about 25 minutes, 345 commands in this process) with the pad alive; the `NextTD 0xFFFFFFFF` / `HeadP changed under the walk` guards never printed, so the guard code itself was not exercised and the race is not shown to be fixed (nor to be gone: before the change the pad died within 5-25 minutes in 3 of 3 long runs: n5/n6/n7). ## 2026-10-19 - frame interpolation (worker i)
**What:** render-side interpolation for the D3D11 presenter, opt-in `RECOMP_INTERP=1` (branch wt/interp; `xboxrecomp/src/kernel/nv2a_hw_interp.inc`, hooks in `nv2a_hw_d3d11.inc`, backup `.bak-20261019i`). Game logic, audio and the 30 Hz flip are untouched; the picture is presented at 60 Hz.

**How it works.** Every clear and draw of the real frame is recorded (bound D3D objects, PS constants, VS header, program constants, copy of the vertex data / HwVertex array, indices). At the flip of frame N the list is replayed into private twin render targets / depth buffers (render-to-texture passes, glow, self-shadow copies included) with each draw moved half way back toward its partner in frame N-1; that image is presented first and the real frame N follows 16.7 ms later from a presenter thread (one half-frame of latency). Draws are matched by key (kind, target surface, vertex program, texture identity, vertex/index count) plus occurrence order; the two display buffers (they alternate and may differ in height, 640x480 vs 640x512) count as one surface class. Blended: program draws = constant registers (if the relative Frobenius change of the moved registers <= 1.0) and the position attribute (if it moved less than 25 % of the draw's extent); CPU-transformed draws = x,y,z,w (w == 1 HUD vertices stay put, move < 75 % of extent and < 160 px). Colours, UVs, fog are not blended. A frame is shown once, without an extra picture, when < 50 % of its draws find a partner (scene change, loading), when > 40 % of the program draws changed by more than 0.5 (camera cut) or when a target was recreated mid-frame. Governor: if the game's own flip interval averages > 36.5 ms the extra work is slowing the simulation, so interpolation is switched off and retried after 4 s (doubling to 30 s).

**Switches.** `RECOMP_INTERP=1` on; `RECOMP_INTERP_GOV=0` (no governor), `RECOMP_INTERP_GOVMS=<ms>`, `RECOMP_INTERP_T` (blend position, 0.5), `RECOMP_INTERP_PROG/HIREL/HIFRAC/ATTR/CPU/CUT` (thresholds), `RECOMP_INTERP_DBG=1|2|3` (`[IP]` line per second; 2: draws that failed to match; 3: constant-change histogram `[IPH]`), `RECOMP_INTERP_DUMP=<prefix>` (with `interp_dump.flag` in the cwd: `_a/_i/_b.bmp` = previous real, interpolated, real). Run-time files in the cwd: `interp_off.flag` (A/B switch), `interp_tune.txt` (thresholds). `[PERF]` now starts with `presents N (x/s)` and a `[PERF-PRES]` line gives the present-interval mean/std/max. Scripts: `pd-game-v2/perfstat_i.py`, `bmp2png_i.py`, `interp_cmp_i.py`, `interp_viz_i.py` (a | i | b strip + difference images).

## 2026-10-19 - interpolation off the guest's critical path (worker i, follow-up)
**Hypothesis confirmed.** With the replay on the executor (ack) thread at the flip, the executor could not answer the guest's flush kicks / draw the next frame for 8-9 ms, so the replay cost was added to the guest's frame: at the Battle Terminal spawn (898 draws) the game fell from ~28 to 18-24 flips/s and the governor kept interpolation off. ## 2026-10-19 - pad stall under load: root cause and fix (worker i)
**Holder identified.** New attribution (always on, no env): `[IRQLLONG]` (outermost CPU-lock hold > 50 ms: tid, role, hold time, guest/host return address at acquire) and `[DPCLONG]` (any DPC > 50 ms: routine, context); `RECOMP_DPC_WATCH=1` samples the DPC thread's RIP every 5 ms once it has run 30 ms (`[DPCWATCH]`, offsets resolved through the link map). The holder of the 07:29 incident was the **D3D vblank DPC (guest 0x24CA70, context 0x2532A8) on the kernel DPC thread**; it held the CPU lock for 50-1800 ms per vblank (also without any stress, 11 times in 4 min of hub walking). `[DPCWATCH]` put it in `sub_0024CC20` (the vblank ISR/DPC body): after acking PCRTC_INTR_0 (write 0x600100) it spins `while (PMC_INTR_0 [0x100] & 0x01000000)`. Nothing clears that bit except the NV2A ack thread, at the top of its loop, i.e. after a whole pushbuffer scan of the frame (heavy frame, load, CPU contention: tens of ms to seconds). Meanwhile the lock was held, the OHCI ISR was deferred and the pad's TDs did not retire (OHCIDEAD), waiters gave up after 200 ms.
**Fix.** The ack of those two registers moved to a small high-priority thread (`nv2a_flush_thread`, xbox_memory_layout.c): it clears PMC_INTR_0 / PCRTC_INTR_0 as soon as the 1.5 ms vblank hold is over (hot for 2 ms after a clear, else Sleep(1); `RECOMP_FLUSH_THREAD=0` = off). ## 2026-10-19 - audio crackle/flutter (worker a)
**Tooling.** `RECOMP_AUDIO_DUMP=<file.wav>` writes the final mix the runtime hands to XAudio2 (up to 30 min, 48 kHz stereo 16-bit, header sizes left 0) plus `<file.wav>.events.txt`: one line per APU event on the same sample timeline (`ON`/`OFF` voice, `SSL` list set, `LISTDONE`, `EMPTY` stream underrun, `LIGHT`/`ACTIVE` frame-thread mode, `DROP` = XAudio2 refused a buffer). Analysis: `dev/audio_analyze.py` (envelope spectrum, clicks, clicks near events), `dev/audio_gaps.py` (digital-silence gaps inside live audio, preceding event), `dev/audio_env.py` (modulation depth per band). `RECOMP_APU_WAV` still works.

**Finding.** The hub dump shows whole-mix digital silence of exactly 288, 544 or 800 samples (256/512/768 + 32) right after a voice goes OFF: 121 gaps in 90 s and 125 in 100 s (about 1.25/s, roughly 1% of the time silent, every voice at once; music included). Cause: `SE2FE_IDLE_VOICE` sets FECTL FEMETHMODE to TRAPPED for every idle voice until DirectSound's service routine unlinks it (delivered from the frame thread after the frame, held off while a guest thread is at raised IRQL). The frame thread tested `fectl & FEMETHMODE_HALTED` (0x80), but TRAPPED is 0xE0 and contains that bit, so a trapped front end was treated as halted and the frame took the "lightweight" path, which `memset`s the whole 256-sample monitor buffer (including the sub-frames already rendered) and renders no voices. 341 LIGHT intervals in a 460 s hub run; their lengths (0/256/512/768 samples: 9/285/49/11) match the gap lengths. On hardware a trapped FE only stops method fetch; the voice processor keeps running. Each retriggered SFX (the hub re-keys one 14080-sample buffer on voices 0x5F/0x64/0x65/0x7F/0x80 about every 0.3 s; the brief's "stream voices" 0x64.. are not streams: `stream 0 loop 0`, ba 0x238B8) therefore punches a hole in whatever else plays (the movie dialogue stream), which is the crackle; the real stream voices (0xF5-0xF7, persist) are fine: no click within +-300 samples of any LISTDONE (3 of 123 near a click in the opening movie dump, same as chance), no EMPTY underrun while it plays, no XAudio2 drops (0 dropped, 1 underrun in 22400).

**Fix** (`xboxrecomp/src/apu/apu_core.c`, backup `.bak-20261019a`): compare the FEMETHMODE field (HALTED vs TRAPPED) so a trapped FE still runs the VP/DSP frame; the lightweight path clears only its own 32-sample slice instead of the whole period. `RECOMP_APU_TRAP_SILENCE=1` restores the old behaviour for A/B. `apu_vp.c` only gained event hooks (backup `.bak-20261019a`).

**Numbers (hub, standing still, in-engine dump).** Before: 125 silence gaps in 100 s (79 x 288, 34 x 544, 5 x 800, ...), LIGHT intervals 341. After: 1 gap in 100 s (448 samples, not next to a LIGHT interval), no LIGHT intervals. Opening movie via attract hook (no SFX voices), before/after: 2 trivial gaps (40/51 samples) in both, clicks 1.4/s and 1.5/s (signal transients, not aligned to the 1024 stage or to packet boundaries), no regression.
